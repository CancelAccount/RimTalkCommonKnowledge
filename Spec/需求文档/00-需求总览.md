## 0. 一句话目标

在新开档（派系已全部生成）时，把世界地图上每个非隐藏派系的**身份、意识形态、与我方关系、领袖与据点**，以及**与该派系相关的异种人（Xenotype）设定**，整理成「常识」写入 RimTalk-Expand Memory 的常识库；玩家与殖民者对话提到该派系名或异种人名时自动带入。

**本期不做**（明确排除，避免范围蔓延）：

- 不挂钩「事件中途新生派系」做增量注入（仅新档 + 读档补齐两处）；
- 不为殖民者个人写「对某派系的私人印象」（那属于记忆扩展的 `targetPawnId` 定向常识，非本 mod 职责）；
- 不做 UI（复用 RimTalk-Expand Memory 自带的常识库界面查看/编辑）；
- **不重复上游已有的「殖民者状态」种族/异种人字段**：上游 `PawnStatusKnowledgeGenerator.GenerateStatusContent` 已把每个殖民者的种族与异种人写进其个人状态条目（形如 `{殖民者}的种族是{种族名}-{异种人名}`，例：「小明的种族是人类-智人种」，证据 ㉖）。本 mod 只写**世界级**异种人设定，二者互补；
- **不覆盖 `PawnKindDef` 级异种人设置**：只读 `FactionDef`/`MemeDef` 级集合（理由与护栏见 01 §RK-9）；
- 不采集玩家自定义异种人（`CustomXenotype`）：世界生成时不存在，且无 Def 可挂标签。

## 3. 决策表（已定案）

| # | 议题 | 定案 | 依据 / 理由 |
| --- | --- | --- | --- |
| D1 | 注入时机 | **`GameComponent.StartedNewGame()`**（新档地图生成完毕后） | 此刻 `Faction.OfPlayer`、初始关系、意识形态、据点均已就绪；`WorldComponent.FinalizeInit(false)` 早于玩家派系创建（证据 ⑩），写不出「与我方关系」 |
| D2 | 注入内容范围 | 基础身份 + 意识形态 + 与我方关系 + 领袖与据点 | 用户选定 |
| D3 | 触发标签 | **仅派系名**（`tag = faction.Name`），`matchMode = Any`；另按 D17 并列特征异种人名 | 用户选定；对话真正提到该派系名才注入，不喧宾夺主 |
| D4 | 旧档 / 中途装模组 | **`GameComponent.LoadedGame()` 校正内容**：缺失则补、陈旧则重写、逐字一致则不动（比对式，见 D19），设置项可关闭（默认开） | 用户选定。**R1.12 / D19 增补**：原定为「仅补齐缺失项」，实测发现这会让好感度与关系**永久停留在开档快照**——读档也不刷新 |
| D5 | 注入 API | `RimTalk.Memory.CommonKnowledgeAPI.AddKnowledgeEx(tag, content, importance, KeywordMatchMode.Any, targetPawnId: -1, canBeExtracted: true, canBeMatched: true)` | 上游对外公开 API，异常内部已 catch 并返回 `null`（证据 ①）；**但取库无空档守卫**（证据 ②），`Current.Game == null` 时必须自行短路。**S2 增补**：原定 `AddKnowledge`，因它无法设置两个扩展开关而改用 `AddKnowledgeEx`（见 D18） |
| D6 | 每派系条目数 | **合并为 1 条 entry**（4 类信息串联为一段无换行文本） | 常识注入名额 `maxInjectedKnowledge` 默认仅 **5**（证据 ㉑），4 条同标签条目会互相挤占名额、且可能只注入一半；合并保证原子性 |
| D7 | 分类显示 | 注入后把 `entry.category` 设为 `KnowledgeEntryCategory.Lore`（= UI 的「世界观」） | `tag` 仅含派系名时 `GetEntryCategory` 会判为 `Other`（证据 ⑦）；显式分类让 RimTalk 常识库 UI 分组更直观 |
| D8 | 幂等标记 | 内容前缀标记（`【派系】`）+ `FindKnowledge(tag)` 扫描判定已注入 | 不额外持久化状态；玩家手动删除后下次读档会补回，登记为已知行为（证据 ⑤：条目本身随存档保存） |
| D9 | 依赖调用方式 | **直接引用 `RimTalkMemoryPatch.dll`**（编译期校验），调用点收敛到单一桥接类 | 该 mod 已是 `modDependencies` 硬依赖（About.xml），编译期签名校验优于纯反射；桥接类隔离，便于将来改反射 |
| D10 | 是否引入 Harmony | **不引入**。零 Harmony 补丁 | 仅两处 `GameComponent` 回调即可覆盖需求；`cj.rimtalk.expandmemory` 已自带 Harmony 依赖，本 mod 无须重复 |
| D11 | **重要性档位（世界观级）** | 一律以**世界观级**注入：`importance = 1.0`（最高档）+ `category = Lore`；`1.0` 可在设置里调低 | 用户要求「以世界观级重要性注入」。上游 `importance` 只是 0\~1 的 float、**无档位枚举**（证据 ㉔），故最高档即 1.0；关键词命中另有 `+0.5` 加分，所以 1.0 能让派系常识在触发时稳居排序首位 |
| D12 | **异种人集合来源** | 只取「有效派系（R1.1 筛选后）」的 `def.xenotypeSet` ∪ 其主理念 `memes[].xenotypeSet`，再按 `BaselinerChance` 补基础异种人 | 用户要的是「**相关**异种人常识」——只写本局世界真会遇到的，避免把 Biotech 全量 Def（含本局不会出现的异种人）铺进常识库。不采集地图 pawn 统计：新档时玩家地图上没有敌对派系成员（证据 ㉕） |
| D13 | **异种人条目形态与双向引用** | 每个异种人 1 条 entry；并被派系条目引用（派系条目写成员构成，异种人条目写出没派系） | 复用 D6 的「合并、省名额」原则；双向引用让殖民者无论提派系名还是异种人名都能拼出完整印象。`PawnStatusKnowledgeGenerator` 已写「个人种族」而不写「世界设定」（证据 ㉖），二者不重复 |
| D14 | **异种人标签口径** | 与 D3 一致：`tag = XenotypeDef.LabelCap`（如「骠骑种」），不走通用词 | 保持精确触发策略；异种人名天然是对话里会出现的专有名词 |
| D15 | **异种人内容前缀与幂等** | 独立前缀 `【异种人】`，与派系的 `【派系】` 分开判定与管理 | 两类条目生命周期、开关、模板都不同，分开前缀便于按类清理与排查（D8 同构） |
| D16 | **统一日志入口** | 所有日志一律经单一静态类 `KnowledgeLog` 输出，禁止各文件直接调 `Log.*`。分级：汇总 `Summary` / 告警 `Warn` / 错误 `Error` **无条件输出**；明细 `Detail` 仅当 `VerboseEnabled`（= 设置值 ∨ `Prefs.DevMode`）为真 | 用户要求「先做统一日志入口」。集中管理前缀与分级，避免口径分裂；`WarnOnce` 直接借用上游 `Log.WarningOnce(text, int key)` 自带去重，防同类告警刷屏（key 须取自 `FactionKnowledgeConfig` 常量，不用裸数字） |
| D17 | **特征异种人并入触发标签** | 若派系成员构成中**占比最高的非基础异种人 chance 严格最大且唯一，且 `> FactionDef.BaselinerChance`**，则把该异种人名并入派系条目的触发标签：`{派系名},{异种人名}`（**半角逗号**分隔，`XenotypeDef.LabelCap`）；并列最大或不满足条件时不并入 | 用户要求「异种人为主的派系，把对应异种人也纳入关键词」。**实测关键**：`CommonKnowledgeEntry.keywords` 字段只被序列化、**不参与任何匹配**（证据 ㉗），触发词只能写进 `tag`，故「纳入关键词」落实为并入 `tag`；判定口径收紧以避免武断结论（RK-14） |
| D18 | **扩展开关一律开启** | 所有条目显式设 `canBeExtracted = true`、`canBeMatched = true`（须用 `AddKnowledgeEx`） | 用户要求「派系常识允许被提取和匹配」。**实测关键**：这两个开关不在 `CommonKnowledgeEntry` 上，而在 `ExtendedKnowledgeEntry` 侧表，`AddKnowledge` 完全不写它们，新建默认 **false**（证据 ㉘）。语义：`canBeExtracted` = 内容可被拼进下一轮链式匹配文本（充当线索）；`canBeMatched` = 可被**第 2 轮起**的链式匹配命中。注意第 1 轮（对白文本直接匹配）**不受** `canBeMatched` 限制，且上游「常识链式匹配」默认关闭（RK-15） |
| D19 | **内容陈旧与定时刷新** | 派系常识的**写入与内容校正共用一套逻辑**：库内无条目 → 写入；逐字一致 → 只校准好感度基准；差异**仅**来自好感度且差值 `< GOODWILL_REFRESH_THRESHOLD`（10）→ 本次不重写；其余情况（关系质变、领袖更替、据点增减、成员变化、模板升级）一律重写。校正时机 = 新档 `StartedNewGame()` + 读档 `LoadedGame()` + `GameComponentTick()` 按 `REFRESH_INTERVAL_TICKS`（2500 tick = 1 游戏小时）节流轮询。异种人条目只做「缺失才补」，**不参与**轮询 | 用户提出「好感度会变，是否得定期与质变时更新」。**确认属实且更严重**：原实现读档走的是「已存在即跳过」，连读档都不刷新。**不止③段**：领袖、据点数量与最近距离同样会变。**零 Harmony（D10）下没有「关系变化」原生事件**，只能轮询——`GameComponentTick()` 每 tick 被 `GameComponentUtility` 调用（证据 ㉚），自节流即可。选**内容逐字比对**而非逐字段判断：一次覆盖全部易变段，且本 mod 升级模板后旧内容会自动升级。**「仅好感度波动」的判定**：把库内内容里的「上次写入的好感度句」整句替换为「当前好感度句」后与新建内容逐字比对，相同即证明其它段未变（好感度句模板固定、数值唯一，替换安全）。**`replaceExisting` 参数随之取消**：原 FR-5.1/5.2 的「新档先删后写 / 读档缺失才补」已被比对式统一覆盖 |
